# SerialPort demo — an interactive tour of a CLI-backed 4D component

This is a small 4D application that consumes
[`miyako/SerialPort`](https://github.com/miyako/SerialPort) as a **Dependency
manager dependency** and puts every part of its API on screen. The component is
CLI-backed: `cs.Serial.SerialPort` launches a bundled native executable through
`4D.SystemWorker` and talks to it over a line protocol. Nothing here needs real
serial hardware — a PTY simulator plays the device.

## What the demo is for

The point is not to print "hello". The point is to show, in one window:

* a session that is created, listed, opened, written to, read from, and shut
  down **without ever blocking the form's event loop**;
* the three reply shapes a caller has to keep apart — a queued acknowledgement,
  a request reply, and unsolicited events such as decoded data and disconnects;
* multibyte text split across chunk boundaries, a binary frame that must survive
  byte for byte, and a stream that keeps arriving;
* a device that stops reading (back-pressure) and how the component reports it;
* five deliberate failures, each of which returns an error instead of a crash.

## Run it

1. Open `Project/SerialPort-demo.4DProject` in 4D 21 R5 (or 21.2 LTS) and run.
2. In the window: **Start device** → **Start session** → **Open** → **PING**.

The first click starts the simulator, which prints the PTY path it bound to
(`/dev/ttysNNN`) and fills the path field. The project resolves the component
from `Project/Sources/dependencies.json`:

```json
{ "version": 2100,
  "dependencies": { "SerialPort": { "github": "miyako/SerialPort", "version": "0.1.2" } } }
```

That is **download mode**: 4D fetches the released ZIP and keeps it outside the
project (`.local-components/`), so this repository never carries a copy of the
component. Nothing in `Project/Sources` is generated by that download.

The map from name to folder lives in `environment4d.json`, which the IDE writes
when it resolves the dependency. Opening the project in 4D therefore resolves it,
but a headless run does not: a fresh clone has neither the component nor the map,
and `tool4d` fails with

```
PackageManager No component to fetch dependencies
PackageManager Dependency 'SerialPort' cannot be found
```

`tools/resolve_dependency.py` closes that gap — it reads the pins, downloads the
release ZIP the Dependency manager would have fetched, unpacks it into
`.local-components/`, restores the ZIP's file modes (the bundled CLI has to stay
executable) and writes `environment4d.json`. Both harnesses call it first, so
they work from a clone with no IDE step:

```sh
python3 tools/resolve_dependency.py           # do it now
python3 tools/resolve_dependency.py --check   # report only
```

## The virtual device

`tools/virtual-serial/virtual_serial.py` opens a pseudo-terminal master, prints
`PORT=<slave path>` and `READY`, then serves a tiny command language:

| command | answer |
| --- | --- |
| `PING` | `PONG <n>` |
| `READ` | `TEMP=21.5;HUM=48.0;SEQ=<n>` |
| `BIN` | a frame with NUL, `0x02`, `0xff` and a sequence number |
| `KANJI` | `温度 21.5` with the first character **split** across two writes |
| `MULTI` | 64 numbered lines, to show truncation limits |
| `STREAM` | toggles a periodic `SEQ=… TEMP=…` line |
| `STALL` | stops reading for a while, so writes back up |

The simulator is started from the window through `4D.SystemWorker`, so it is
also a small demonstration of the same mechanism the component uses.

## Architecture, and why it looks like this

```
window process                      owner worker                    CLI process
─────────────────                   ──────────────                  ───────────
form timer → SerialDemoPump    →    SerialDemoWorker   →            4D.SystemWorker
  reads Logs/session-status.json      submits commands                  serial-port serve
  applies new messages                handles callbacks                       │
  never owns the session              publishes status+outbox                 ▼
                                                                           PTY slave
```

The component needs a **live worker event loop** for its callbacks, and a
SystemWorker callback cannot be delivered into a form's process. The two
processes therefore exchange a document instead of an object:

* the worker appends numbered messages to `outbox` in
  `Logs/session-status.json` and rewrites the snapshot fields
  (`phase`, `ports`, `connections`, `stats`, `text`);
* the window polls that file on its form timer and applies only messages whose
  `seq` is greater than the cursor it last applied (`SERIAL_AppliedSeq`).

Polling instead of `CALL FORM` was not the first attempt; see
[Documentation/chokepoints.md](Documentation/chokepoints.md) for the two designs
that failed and what they taught.

## Points of interest in the window

* **Session** — `start` reports the target it bound to (`macOS-universal`), and
  `shutdown` / `terminate` are different: one drains, one kills.
* **Ports and connection** — `list` returns the machine's real ports; the PTY
  appears there too. `Open` takes path plus the four line settings.
* **Failure showcase** — each button is a case the component must reject:
  missing path, unknown connection, `baudRate: 0`, a 40 000-byte write, and a
  `cancel` for a request that does not exist. All five arrive as `error`
  messages, and the session keeps running.
* **Send / Receive** — presets exercise text, hex bytes, split UTF-8, binary and
  a stream; the decoder below the listbox keeps partial multibyte sequences
  until the next chunk completes them.
* **Virtual device transcript** and **Event log** — every message the worker
  published, in order, with its kind, so the pull architecture is visible.

## Tests

Two harnesses, both using the simulator, so they need no hardware:

```sh
python3 tools/run_smoke.py        # headless, tool4d, 12 cases, ~5 s
python3 tools/run_ui_smoke.py     # opens the real window, 11 assertions, ~3 s
```

`run_smoke.py` starts tool4d with `--startup-method=SerialPortDemoTest`; the
tests live in `SerialPortDemoTestWorker`. `run_ui_smoke.py` launches the full
application with `--startup-method=SerialPortDemoUIRun`, and
`SerialPortDemoUIDriver` presses the demo's own buttons while the window stays
in its event loop. The second one is the only way to prove that the pull
architecture really updates the form.

Verification actually performed here (arm64 macOS):

| check | result |
| --- | --- |
| headless suite, tool4d 21R4 (100224) | **12/12 passed**, 4.1 s |
| window suite, 4D 21 R5 (100175) | **11/11 passed**, 2.9 s |
| dependency resolved in download mode | passed (IDE-resolved, and re-resolved from a fresh clone by `tools/resolve_dependency.py`) |
| Windows x64 / Intel macOS 4D | **not run** — no runtime available here |
| real serial hardware | **not run** — the simulator stands in |

## Findings

Everything surprising that this project hit — 4D semantics, path rules, PTY
behaviour, component limits — is written up in
[Documentation/chokepoints.md](Documentation/chokepoints.md). It is the part
worth reading if you plan to build another CLI-backed component.
